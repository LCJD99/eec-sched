# EvoScheduler 第二版 PSOCM

## 1. Problem

### 1.1 Problem Statement

> **如何面向端边云 Agentic Workflows，自动生成能够根据 Workflow 与系统证据作出节点 Configuration 和 Device 分配的可执行 Scheduler 策略？**

本文研究的对象不是某一次请求的静态 placement，而是一个可复用、可执行的 Scheduler 策略。该策略接收一个已经规划完成的 Agentic Workflow 及其相关系统证据，为 Workflow 中的每个节点选择执行 Configuration 和 Compatible Device。具身问答是本文采用的代表性 workload，但问题本质是更一般的端边云 Agentic Workflow Scheduling。

本文不把 Workflow Planning 与 Scheduling 混为一体。Planner 决定工具调用及其依赖关系；Scheduler 不改变 Workflow 结构、工具依赖或执行顺序，只决定每个既定节点“采用什么 Configuration、放在哪台 Compatible Device 上执行”。

### 1.2 Input

- **Agentic Workflow**：由 Planner 产生的设备无关 Tool-Call DAG，包含工具节点、数据依赖和最终输出。
- **Configuration Evidence**：每个工具可选 Configuration 的语义质量证据。
- **End-Edge-Cloud Evidence**：Configuration 在 Device、Edge 和 Cloud 上的兼容性、执行开销及设备间通信开销。
- **Scheduling Objective**：用于表达 quality、latency 和 resource consumption 权衡的评分上下文。

自然语言请求、图像或其他原始任务输入由 Planning 阶段转化为 Workflow；它们不是 Scheduler 直接修改的对象。

### 1.3 Output

输出是一个具有明确版本的**可执行 Scheduler 策略**。对于任意合法的 Workflow 和系统证据，该策略为每个节点返回：

\[
\text{node} \mapsto (\text{Configuration},\ \text{Compatible Device}).
\]

可信系统负责验证 assignment、确定规范执行顺序、模拟执行与通信、测量 Scheduler 自身耗时并计算反馈。Scheduler 不能自行声明其结果是否合法或得分多少。

### 1.4 Significance

Agentic Workflow 将多个具有不同语义能力和资源需求的模型与工具组合起来。进入端边云环境后，同一个 Workflow 还会受到设备能力、通信路径和执行 Configuration 的共同影响。因此，调度质量不再只是传统意义上的计算节点 placement，而是语义质量、端到端时延和资源消耗之间的跨层权衡。

现有方法通常依赖专家手工设计规则、问题专用优化器，或者预先定义状态、动作和策略表示的学习方法。这些方案不仅带来较高的建模、调参和训练成本，也限制了系统自动形成新调度逻辑的能力。自动生成可执行 Scheduler 策略，有机会把调度器设计从一次性的人工工程活动转化为由系统反馈驱动的程序搜索过程。

## 2. SoTA & Limitations

### 2.1 二维研究版图

本文从场景和技术两个相互独立的维度组织现有工作。

**场景维度**区分：

- **相对固定的传统 Workflow / Combinatorial Workload**：任务结构、算子语义及优化对象通常由问题定义预先给定。
- **Agentic Workflow**：异构模型与工具通过动态依赖组合，执行结果同时受到任务语义、工具能力和系统资源的影响。

**技术维度**区分：

- **人工规定的优化或策略结构**：人工启发式、数学优化和学习型方法需要预先规定规则结构、变量空间、策略表示或更新方式。
- **LLM 生成和迭代可执行策略程序**：LLM 生成或修改决策逻辑，并通过外部 evaluator 的反馈反复搜索。

| | 人工规定的优化或策略结构 | LLM 生成和迭代可执行策略程序 |
|---|---|---|
| **相对固定的传统 Workflow / Combinatorial Workload** | 传统 workflow scheduling、人工启发式、数学优化与 RL；例如 [Vulcan: Automatic Query Planning for Live ML Analytics](https://www.usenix.org/conference/nsdi24/presentation/zhang-yiwen) 在人工规定的 query-planning 结构中联合搜索 pipeline、configuration 与 placement | [FunSearch](https://www.nature.com/articles/s41586-023-06924-6)、[EoH](https://proceedings.mlr.press/v235/liu24bs.html)、[ReEvo](https://proceedings.neurips.cc/paper_files/paper/2024/hash/4ced59d480e07d290b6f29fc8798f195-Abstract-Conference.html) 和 [ReVEL](https://arxiv.org/abs/2604.04940) 等面向具有明确 evaluator 的数学或组合优化问题生成启发式程序；[Vulcan: Instance-Optimal Systems Heuristics Through LLM-Driven Search](https://arxiv.org/abs/2512.25065) 与 [SchedCP](https://mlforsystems.org/assets/papers/neurips2025/paper32.pdf) 已进一步将程序生成用于系统策略 |
| **Agentic Workflow** | 通过声明式 Workflow、profile-guided optimizer 或 adaptive runtime 优化模型、硬件和执行配置；例如 [Murakkab](https://www.usenix.org/conference/osdi26/presentation/chaudhry) 和 [LLM-as-Scheduler](https://aclanthology.org/2026.acl-long.581/) | **Ours：利用保留 Workflow 条件—调度决策—多目标系统后果关系的细粒度 Trace 上下文，迭代完整可执行 Scheduler 策略** |

这个四宫格不是简单地把工作分成“使用 LLM”和“不使用 LLM”，也不假设任何方法拥有真正不受约束的开放搜索空间。FunSearch、EoH、ReEvo 及系统策略生成工作仍然需要开发者给出接口、程序骨架或 evaluator。技术轴的关键区别在于：求解器是在开发者预先规定的决策逻辑中选择参数或动作，还是让 LLM 根据反馈生成和修改决策逻辑本身。

这是一项基于当前核查工作集合的范围性定位，而不是“首次提出”的穷尽式空白声明。已有研究已经覆盖 cross-layer Agentic Workflow optimization、LLM 参与 Workflow scheduling、LLM 驱动的系统策略生成，以及从 trajectory 中进行反思。本文需要证明的更窄差异是：针对 Agentic Workflow 的端边云跨层调度，如何在上下文预算内保留 Workflow 条件、节点级 Configuration/Device 决策及其 quality、latency、communication、resource 和 failure 后果，并据此可靠地迭代完整 Scheduler 策略。

### 2.2 L1：Agentic Workflow 的语义—系统耦合缺少统一反馈表示

传统调度问题通常可以预先给定任务结构、运行代价和优化目标。Agentic Workflow 则同时包含三个相互关联的层面：工具依赖决定执行与传输路径；工具 Configuration 影响语义质量；Configuration 与 Device 的组合又决定计算和通信开销。单独优化 placement、模型选择或资源分配，无法完整表达这些决策之间的相互作用。

因此，场景维度上的核心限制不是 Agentic Workflow “规模更大”或“运行更慢”，而是现有调度抽象难以把 Workflow 语义、Configuration 质量以及端边云系统代价统一转化为明确的决策空间和可计算反馈。

### 2.3 L2：现有方法受限于预定义的策略结构

人工启发式、数学优化和学习型调度方法的求解手段虽然不同，但通常都要求开发者预先规定规则、变量、策略表示或更新机制。人工启发式需要持续投入专家经验；问题专用优化器需要反复建模；RL 等学习方法还需要设计状态、动作、奖励和训练流程，并承担相应的训练与调参成本。Murakkab 已经证明声明式 Workflow 与跨层优化能够改善 Agentic Workflow 的资源效率，因此本文不能把 cross-layer visibility 本身作为独有贡献；其调度逻辑仍建立在开发者规定的 MILP 变量和 adaptive runtime 机制上。

这些工程成本是表层表现。更根本的限制是：当 Workflow、工具组合或系统证据发生变化时，现有方法仍被限制在预定义的策略结构中，难以直接从新的执行反馈里形成和修改可执行调度逻辑。

另一方面，LLM program evolution 已经能够修改启发式、prompt 乃至系统 policy。[ReEvo](https://proceedings.neurips.cc/paper_files/paper/2024/hash/4ced59d480e07d290b6f29fc8798f195-Abstract-Conference.html) 使用 pairwise fitness 与长短期 reflection，[ReVEL](https://arxiv.org/abs/2604.04940) 使用 performance-profile grouping 和多轮反馈，[GEPA](https://proceedings.iclr.cc/paper_files/paper/2026/hash/0e9e708b6f48e14fd0ac29e167413f76-Abstract-Conference.html) 则从 compound-AI trajectory 中进行反思。因此本文不能把“使用结构化反馈”或“让 LLM 阅读 Trace”本身作为充分 novelty；核心问题必须进一步限定为 Agentic Workflow 调度中特有的、具有可信来源和跨层调度语义的 Trace 表示与信息选择。

## 3. Opportunity

Agentic Workflow 的跨层耦合虽然增加了调度难度，却也带来了新的可观测性和可控性。Workflow 可以表示为显式的工具依赖图；不同 Configuration 的语义质量、设备执行开销和设备间通信开销可以通过 profiling 与执行记录获得。过去隐含在应用逻辑和运行系统中的关系，因而可以被展开为“Workflow 条件—调度决策—系统后果”的可计算链路。这使得建立统一调度模型和明确反馈成为可能，对应 L1。

与此同时，系统执行 Trace 并不只包含一个最终分数。它还记录了在什么 Workflow 和系统条件下作出了哪些调度决策，以及这些决策产生了怎样的质量、时延、资源开销、失败或回退。LLM 已经具备理解代码、结合上下文进行推理并生成可执行程序的能力。如果能够从大量 Trace 中提取真正影响策略效果的信息，并保持决策与结果之间的关系，这些执行历史就可能成为自动生成和改进 Scheduler 的有效反馈，对应 L2。

## 4. Challenges

### C1：如何建立反馈明确的跨层调度模型？

> **如何统一建模 Agentic Workflow 的语义质量与端边云系统代价，使 Scheduler 的组合决策能够获得明确、可信的优化反馈？**

模型既要表达 Workflow 依赖、Configuration 和 Device 的离散组合决策，也要表达语义质量、执行时延、通信代价和资源消耗之间的关系。同时，反馈必须由 Scheduler 之外的可信环境产生，否则待优化程序可以通过修改评价逻辑或伪造结果获得高分。

### C2：如何让 LLM 从复杂 Trace 中获得有效进化信息？

> **如何从复杂系统 Trace 中提取具有判别力的调度证据，并将其转化为 LLM 可理解的有效上下文，从而生成和改进可靠的 Scheduler 策略？**

只提供 Candidate 总分无法说明策略为何成功或失败；把所有原始 Trace 全部塞入上下文，又会造成信息冗余、关键反例被淹没以及错误归因。真正的困难是保留 Workflow 条件、调度决策和执行后果之间的关系，并选择能够帮助模型比较、归因和提出改进假设的信息。

## 5. Model / Design

### 5.1 M1：RL-inspired Feedback-Explicit Scheduling Model

M1 将系统表示为两个相互嵌套的优化层次。它借用[强化学习](http://incompleteideas.net/book/RLbook2020.pdf)中 observation、policy、action 和 reward 的概念组织问题，但不把本文方法宣称为 RL 算法。

#### 内层：一次 Workflow 的结构化上下文决策

对于 Trace \(i\)，令：

\[
x_i=(G_i,D_i,w_i),
\]

其中 \(G_i\) 是固定 Tool-Call DAG，\(D_i\) 是版本化的 Configuration、Device、Execution 与 Transfer Evidence，\(w_i\) 是质量、时延和资源权衡所需的评分上下文。可信环境据此构造 Scheduler 可见的只读 observation：

\[
o_i=\operatorname{View}(x_i).
\]

可执行 Scheduler 策略 \(\pi\) 一次产生完整联合动作：

\[
a_i=\pi(o_i)
=\{v\mapsto(c_v,d_v)\mid v\in V(G_i)\},
\]

其中 \(c_v\) 是节点 \(v\) 的 Configuration，\(d_v\) 是 Compatible Device。DAG 节点不是 RL time step；Scheduler 不会分配一个节点后观察新状态，也不能控制规范执行顺序。

可信 evaluator \(E\) 独占 validation、Scheduler timing、execution/transfer simulation 和 scoring 权力：

\[
e_i=E(x_i,a_i)
=\bigl(z_i,q_i,l_i,r_i^{resource},u_i,\tau_i\bigr),
\]

其中 \(z_i\) 是合法、拒绝或失败状态，\(q_i\)、\(l_i\) 和 \(r_i^{resource}\) 分别表示语义质量、端到端时延和资源结果，\(u_i\) 是用于比较的 scalar utility，\(\tau_i\) 是保留完整决策与后果的系统 Trace。

这里的 utility 可以由质量、时延和资源指标组合而成，但各分项必须同时保留。标量反馈用于形成明确 fitness，分解后的 Trace 证据则供 M2 理解策略行为。

#### 外层：跨 Workflow 的 Scheduler 策略优化

在固定的评价 Trace 集 \(\mathcal T\) 上，Scheduler 策略的目标为：

\[
J(\pi;\mathcal T)
=\frac{1}{|\mathcal T|}\sum_{i\in\mathcal T}u_i.
\]

因此，内层回答“这一次完整 assignment 的效果如何”，外层回答“这个可执行 Scheduler 在一组不同 Workflows 上是否具有更好的整体策略”。M2 搜索的是 \(\pi\) 所代表的程序逻辑，而不是单次动作，也不是神经网络参数。

M1 的关键作用是把复杂系统执行转化为两类互补反馈：

1. 用于可靠比较 Candidate 的明确 fitness；
2. 用于解释 Candidate 行为的细粒度 Trace evidence。

### 5.2 M2：Trace-informed LLM Evolutionary Scheduling System

M2 是完整的 Scheduler 策略生成系统，而不是一个孤立的上下文压缩算法。它包括 Scheduler Candidate 管理、可信评价、Trace 信息处理、进化搜索、Reflection 和 Scheduler 代码生成。贯穿整个架构的核心逻辑是：**把系统 Trace 转化为 LLM 能够理解和利用的有效上下文。**

#### 5.2.1 系统闭环

```text
Initial Scheduler Candidates
→ M1 Trusted Evaluation
→ Candidate Fitness + Full System Traces
→ Evolutionary Candidate Selection
→ Trace Evidence Abstraction and Selection
→ LM-readable Evolution Context
→ Reflection and Scheduler Code Generation
→ New Executable Scheduler Candidate
→ M1 Trusted Evaluation
```

进化算法负责维护候选程序、选择父代并组织多轮搜索；LLM 负责理解被选中的系统证据，并生成或修改 Scheduler 程序；M1 的可信环境负责判断新程序是否真的改善。任何模型生成的解释和分数声明都不能替代可信评价。

#### 5.2.2 Trace Evidence Abstraction

原始 Trace 同时包含 Workflow、系统证据、节点 assignments、执行与传输过程、质量、时延、资源结果以及失败信息。M2 首先把这些深层对象投影为与策略进化有关的证据，至少保留：

- 证据产生时的 Workflow 和系统条件；
- Candidate 作出的 Configuration 与 Device 决策；
- 相比父代或对照策略发生变化的决策；
- quality、latency、resource consumption 和状态结果；
- 决策变化与结果变化之间可以被验证的对应关系；
- 原始可信 Trace 的引用。

这种表示的目标不是把 Trace 改写成更短的自然语言摘要，而是让 LLM 能够读懂“在什么条件下，哪个决策产生了什么后果”。数值分解和差异应由可信代码确定性计算，而不是让 LLM 从原始日志中自行猜测。

#### 5.2.3 Informative Context Construction

系统不会把所有历史 Trace 无差别地放入 prompt，而是围绕当前要改进的 Candidate 构造规模受控的 Evolution Context。上下文应优先覆盖能够区分策略假设的证据，例如：

- 代表性失败或低效案例；
- 与失败案例条件相近但结果成功的对照案例；
- 相对父代出现明显进步或回退的案例；
- 容易被新策略破坏的历史 Replay 或边界案例；
- 当前上下文未覆盖哪些证据的显式说明。

长期 Memory 为该阶段提供历史 Trace、Replay 和带证据引用的 Strategy Insights。Memory 的职责是帮助系统寻找相关历史证据，而不是直接改变 fitness、评价规则或当前 Candidate Pool。本文因此研究历史信息如何改善 Trace Context，但不把问题扩大为在线 continual learning。

#### 5.2.4 Context-guided Reflection and Program Evolution

Reflection 不应只输出宽泛的“优化代码”建议，而应根据上下文建立可验证的策略判断：观察到了什么现象、可能原因是什么、哪些证据支持或反对该判断、建议改变什么调度逻辑，以及预期哪些指标发生变化。Coding Agent 再结合该判断和父代 Scheduler 源码生成新的完整策略。

新 Candidate 必须重新运行完整评价 Trace 集。只有可信 evaluator 观察到的实际结果才能支持或反驳 Reflection，而不能依据 LLM 自己的解释接受一次改动。由此形成：

```text
Observe Trace
→ Construct Informative Context
→ Form Strategy Hypothesis
→ Generate Scheduler Program
→ Evaluate on Full Trace Set
→ Confirm or Reject the Hypothesis
```

#### 5.2.5 当前实现与目标设计的边界

当前项目已经实现单次 Evolution Loop、Evolution Graph、Scheduler mutation/crossover、逐 Trace 可信评价、Reflection/Coding 分工和独立 Final Evaluation。当前 Reflection 仍直接接收选中的完整 Trace 对象。

目标设计将在此基础上增加确定性的 Trace evidence representation、对比式信息选择、受预算约束的 Evolution Context，以及从历史 Trace 中检索 Replay 与 Strategy Insight 的能力。这些内容属于第二版的 Model/Design 和后续实现目标，不能在完成实验前表述为已经验证的系统能力。

## 6. Contributions

### 6.1 Conceptually

- 提出面向端边云 Agentic Workflow 的**可执行 Scheduler 策略自动生成问题**，具身问答作为代表性 workload。
- 将 Agentic Workflow Scheduling 表述为“明确系统反馈驱动程序级策略搜索”的问题，而不是单次 placement 或固定策略结构内的参数优化。
- 指出系统 Trace 的价值不只在于产生 fitness，还在于保留调度决策及其后果，为策略生成提供可解释反馈。

### 6.2 Technically

- 提出 RL-inspired Feedback-Explicit Scheduling Model，统一描述 Workflow 依赖、Configuration 语义质量、端边云执行与通信代价，并为 Scheduler Candidate 产生可信 fitness 和细粒度 Trace evidence。
- 构建 Trace-informed LLM Evolutionary Scheduling System，通过程序级搜索生成和评价可执行 Scheduler 策略。
- 提出以“决策—结果关系”为核心的 Trace evidence representation 与 informative context construction，使 LLM 从有限上下文中理解成功、失败和回退，而不是只读取总分或堆叠全部 Trace。
- 引入由历史 Trace、Replay 和 Strategy Insight 支撑的证据检索，同时保持 Memory、模型解释与可信评价之间的权限隔离。

### 6.3 Experimentally

实验应围绕三层证据组织，而不能只报告最终 Candidate Score。

1. **验证 M1 的表达能力**：检查模型是否能够反映 Workflow 结构、Configuration、Device placement、通信路径以及 quality–latency–resource trade-off，并验证可信评价的一致性。
2. **验证完整 M2 的策略生成能力**：与人工启发式、传统优化或 reference scheduler、RL scheduler、直接 LLM 生成以及一般 LLM heuristic evolution 方法比较最终性能、生成成本和跨 Workflow 泛化。
3. **验证 Trace Context 的必要性**：至少比较 scalar-fitness evolution、ReEvo-style pairwise reflection、ReVEL-style performance-profile grouping、GEPA-style full-trajectory reflection，以及本文的调度语义 Trace Context；进一步消融全部 Trace、无对比选择、无历史证据和无结构化 Reflection 等变体，测量进化收益、有效 Candidate 比例、收敛速度、上下文成本及回退风险。

候选评价指标包括：

- **Task / quality**：Workflow completion、任务成功或与具体 workload 对应的语义质量指标；
- **System**：端到端时延、资源消耗、通信开销和调度求解时间；
- **Evolution**：相对初始策略和 baselines 的改进、有效 Candidate 比例、达到目标性能所需轮数与 token/evaluation cost；
- **Context**：单位上下文预算带来的策略提升、关键反例保留率，以及 Reflection 假设被后续评价支持或反驳的比例。

在真实测量、RL baselines、Trace Context 模块和对应消融完成前，本文不预先声称性能提升、真实端边云部署效果或持续学习能力。
